# Zoro-1 장애 대응 에이전트

나중에 다시 볼 때를 위한 설명이다. 2026-11-19에 Trillion Agent AI Hackathon 2026(트랙 1)용으로 만들었다.

작은 테스트 서비스에 장애를 일부러 넣고, 에이전트가 그것을 알아채서 조치하고, 조치가 통했는지 확인하고, 안 되면 사람에게 넘기는 과정을 처음부터 끝까지 돌려 본다. 판단이 필요한 곳(진단, 조치 후 검증, 다음 단계 선택)은 트릴리온랩스의 Zoro-1 모델이 맡고, 무엇을 몇 번까지 해도 되는지는 코드가 정한다.

## 구조

```
정상 클라이언트 x4 ──> nginx ──┬─> 주 앱(app) ───────┐
                              └─> 예비 앱(standby) ──┴─> PostgreSQL
                                  (평소에는 트래픽 없음)

호스트에서 도는 것
  에이전트(agent/agent.py) ──HTTP──> Zoro-1 서버(:8765)
  화면 서버(web/server.py, :8090)
  둘 다 logs/ 아래 기록을 읽는다
```

- 테스트 서비스는 Docker Compose로 뜬다. 클라이언트 4개가 경로 두 개를 각각 초당 1건씩 호출한다(합쳐서 초당 8건, 제한 시간 2초).
  - `/api/orders`: DB를 읽는 경로. 화면에서는 "DB 의존 경로".
  - `/api/ping`: DB 없이 응답하는 경로. 화면에서는 "경량 경로".
- 에이전트는 컨테이너 밖(호스트)에서 돌면서 클라이언트 요청 기록과 nginx 접근 기록을 읽는다. 1초마다 최근 5초를 본다.
- Zoro-1은 따로 띄운 작은 HTTP 서버가 들고 있다. 에이전트를 고쳐 다시 켜도 모델을 다시 불러오지 않고, 이 서버를 끄면 "모델 호출 실패" 상황을 그대로 만들 수 있다.

## 에이전트가 하는 일

1. **평소 기준 재기.** 켤 때 10초 동안 경로별 p95 지연과 요청량을 잰다. 그래서 서비스가 정상일 때 켜야 한다.
2. **진단.** 매초 5초 창과 평소 기준을 Zoro-1에 주고 `normal / app_down / source_flood / slow / unknown` 중 하나를 받는다.
3. **사건 열기.** 같은 이상 판정이 0.7 이상으로 두 번 나오고(그 사이 새로 끝난 요청 5건 이상), 측정값으로 계산한 규칙 판정도 정상이 아닐 때만 연다. 모델만 이상이라고 하면 "보류"로 남기고 아무것도 하지 않는다.
4. **조치.** 진단별로 허용된 조치를 코드가 고른다. 앱 다운과 지연은 앱 재시작, 요청 폭주는 출발지 제한이다. 사건당 2회까지이고 DB 재시작은 자동으로 하지 않는다.
5. **검증.** 조치가 끝난 뒤에 시작한 요청만 센다. 전체 20건, 경로마다 5건 이상 끝나야 판단한다. 모델 판정이 측정값과 같고, 새 요청이 쌓인 뒤 같은 판정이 한 번 더 나오면 확정한다. 30초 안에 확정하지 못하면 "판정 불일치" 또는 "판정 미확정"으로 넘긴다.
6. **다음 단계 선택.** 지연 사건이 재시작 후에도 그대로면 바로 넘기지 않는다. 코드가 후보를 만들고 Zoro-1이 고른다.
   - 점검 전 후보: 새 요청 더 관측 / 예비 앱 점검 / 담당자 이관. 모델에는 주 앱 관측만 준다.
   - "예비 앱 점검"이 0.7 이상이면 예비 앱에 주문 조회 5건을 실제로 보낸다.
   - 점검 후 후보: 새 요청 더 관측 / 예비 앱으로 전환 / 담당자 이관. 앞의 관측에 점검 결과만 더해 준다.
   - 전환은 0.7 이상이고 점검 결과가 코드 기준(90% 이상 성공, 평소보다 훨씬 느리지 않음)도 넘을 때만 한다.
   - 0.7에 못 미치면 새 요청이 쌓인 뒤(점검 후라면 다시 점검한 뒤) 다시 묻는다.
7. **전환.** nginx 설정을 예비 앱으로 바꾼다. 바뀐 설정을 거친 주문 조회가 실제로 응답하는 것을 확인한 뒤에야 성공으로 기록한다. 확인하지 못하면 설정을 되돌리고 넘긴다. 복구 여부는 그 뒤 정상 클라이언트 요청으로 5번처럼 검증한다.
8. **넘긴 뒤.** 그 사건에는 더 조치하지 않고 보고서를 남긴다. 측정값이 정상으로 돌아오면 "감시 재개"만 기록한다(사건은 사람 몫으로 남는다). 넘긴 장애가 계속되는 중에 다른 유형이 보이면 경보만 남긴다.

모델 서버가 응답하지 않으면 규칙 판정으로 이어 간다. 규칙 판정은 평소에도 같이 계산해서 기록에 남긴다.

## 장애 시나리오

| 명령 | 넣는 장애 | 기대하는 흐름 |
|---|---|---|
| `scenario.py app_down` | 주 앱 컨테이너를 강제 종료 | 재시작 → 복구 확인 |
| `scenario.py orders_fault` | 주 앱에서만 주문 조회가 멈춤. 재시작해도 남고 예비 앱은 정상 | 재시작 → 미복구 → 예비 앱 점검 성공 → 전환 → 복구 확인 |
| `scenario.py db_delay` | DB 쿼리에 3초 지연 | 재시작 → 미복구 → 예비 앱 점검 실패 → 전환 없이 이관 |
| `scenario.py reset` | 전부 정상으로 되돌림 | |

뒤의 두 장애는 주 앱에서 보이는 증상이 같다. 예비 앱을 점검해 봐야 갈린다는 점이 이 프로젝트에서 보여 주고 싶었던 장면이다.

## 실행 방법

준비물은 Docker와 Python이다. 모델은 Hugging Face의 `trillionlabs/Zoro-1`인데 접근 동의가 필요하다.

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/hf auth login
.venv/bin/hf download trillionlabs/Zoro-1 --local-dir models/Zoro-1
./demo.sh
```

`demo.sh`가 테스트 서비스, Zoro-1 서버, 화면 서버, 에이전트를 차례로 켠다. 끝나면 `http://localhost:8090/#live`를 열고 다른 터미널에서 장애를 넣는다.

```bash
.venv/bin/python scenario.py orders_fault
.venv/bin/python scenario.py reset
```

- 시나리오 사이에는 반드시 `reset`을 하고 15초쯤 둔다. 전환이 일어난 뒤에는 트래픽이 예비 앱에 남아 있기 때문이다.
- `./demo.sh clean`은 지금까지의 기록을 `logs/archive/`에 보관하고 빈 화면으로 다시 시작한다. `./demo.sh stop`은 전부 끈다.
- 다른 컴퓨터에서 화면을 보게 하려면 `WEB_HOST=0.0.0.0 ./demo.sh`로 켠다. 그때는 `OPERATOR_TOKEN`도 정해 두어야 아무나 "담당자 인수"를 누르지 못한다.
- 서버의 NVIDIA 드라이버가 오래됐으면 최신 torch가 GPU를 못 쓴다. 대처법은 `requirements.txt` 주석에 있다.

## 화면

- `http://localhost:8090/#live`: 실시간. 맨 위 카드가 현재 결론, 그 아래가 단계 줄, "다음 단계 선택" 표(관측 → 후보 → 선택과 확률 → 실행), 요청 기록 그림, 조치 전후 표, 판정 기록 순이다.
- `http://localhost:8090/`: 기록 재생. 11-19 18:27의 첫 통합 실행 두 건(앱 다운 복구, DB 지연 이관)을 다시 보여 준다.
- 화면 읽는 법은 `web/guide.html`과 `화면_읽는_법.pdf`에 그림과 함께 정리했다. 다만 예비 앱 기능을 붙이기 전의 화면 기준이다.

`agent.py` 맨 위의 숫자들: `CONF`(0.7, 판정을 받아들이는 최소 확률), `MIN_SAMPLES`(20), `MIN_NEW`(5), `VERIFY_TIMEOUT`(30초), `MAX_ACTIONS`(2), `PROBE_N`(5).

## 실행 기록 (`runs/`)

- `2026-11-19_first_integration_*`: 첫 통합 실행. 재생 화면이 이 기록을 쓴다.
- `2026-11-19_nextstep_*`, `nextstep_reports/`: 예비 앱 점검과 전환을 붙인 날 밤의 실행 15건과 이관 보고서.
- `2026-11-19_final_check_*`: 결함 두 개를 고친 뒤 세 시나리오를 한 번씩 돌린 기록.

기록 한 줄이 판정이나 조치 하나다. `next_step` 줄에는 모델에 준 관측, 후보, 선택과 확률이 있고 `probe` 줄에는 실제 점검 결과가 있다.

## 확인한 것 (2026-11-19 밤, M3 Max)

| 시나리오 | 실행 | 결과 |
|---|---|---|
| 앱 다운 | 3회 | 3회 모두 복구 확인 (감지부터 4~5초) |
| 주 앱만 주문 실패 | 11회 | 11회 모두 예비 앱 점검을 고르고 전환까지 실행. 복구 확인 9회(14~46초), 이관 2회 |
| DB 지연 | 4회 | 4회 모두 점검 실패 후 이관. 전환 0회 |

- 이관 2회 중 1회는 버그였다(전환 직후 요청 1건이 아직 주 앱으로 가서 미복구로 판정). 고쳤다. 나머지 1회는 아래 약점 때문에 30초 안에 복구를 확정하지 못한 경우다.
- 구현 전 사전 테스트(`zoro_nextstep_test.py`)에서는 문구를 정한 뒤 처음 보는 사례 72건에서 72건 모두 기대한 선택을 했고, 그중 0.7 이상은 60건이었다.
- NVIDIA Brev(L40S) 서버에도 같은 코드를 올려 돌렸다. 모델 호출 한 번이 서버에서는 약 48ms, 이 Mac에서는 약 0.4초다.

만들면서 고친 굵직한 결함들:
- 정상 상태인데 모델이 "지연"이라고 해서 앱을 재시작하던 문제. 측정값도 이상일 때만 사건을 열게 했다.
- 검증에서 모델과 측정값이 다를 때 모델 말만 믿던 문제. 다르면 보류하고, 끝까지 다르면 "판정 불일치"로 넘긴다.
- 한 경로의 결과가 아직 없는데(전부 응답 대기) 복구를 선언하던 문제. 경로별 최소 표본을 두었다.
- 전환 준비 확인이 주 앱의 응답으로도 통과하던 문제. 전환된 설정을 거친 응답만 인정한다.

## 알려진 약점과 하다 만 것

- **확률이 0.7 근처에서 흔들린다.** 선택 자체는 맞는데 0.65~0.75 사이를 오가서 "보류"가 반복되거나 복구 확정이 30~45초 걸린다. 평소 기준값이 조금만 달라져도 확률이 바뀐다. 지연을 평소 기준과 비교하는 일을 모델이 잘 못한다.
- **모델이 규칙보다 나은 점을 보이지 못했다.** 다음 단계 질문은 선택지마다 조건을 써 준 문구라서 같은 사례를 `if` 몇 줄로도 맞힌다. 확인된 것은 "정해 준 절차를 안정적으로 따른다"까지다.
- **검증 질문에 넣는 조치 이름을 골랐다.** 전환을 `switch_to_standby`라고 적으면 같은 관측에서도 복구 확률이 낮게 나와서 `failover_to_standby_app`으로 적는다. 기록 22건으로 고른 것이라 근거가 얇다.
- **요청 폭주는 돌려 보지 않았다.** 진단 선택지와 출발지 제한 조치는 코드에 있지만 주입 스크립트를 만들지 않았다.
- **앱 재시작의 성공 기록.** 재시작 명령은 성공했지만 10초 안에 응답이 없는 경우도 성공으로 기록한다. 전환 쪽만 고쳤다.
- **경계 사례.** 예비 앱 점검이 일부만 성공하는 경우, 표본이 기준 근처인 경우는 실제 실행에서 보지 못했다.
- 모델에 주는 상태와 질문은 영어로 썼다. 한국어로 썼을 때와 비교해 보지는 않았다.
